# Reviewing a flow before execution

kazeflow supports a caller-controlled sequence for code written by a person or
generated by an AI:

1. Define or select the assets and construct a `Flow`.
2. Call `Flow.plan(run_config)`.
3. Review the returned `FlowPlan` and decide whether the selected work is
   acceptable.
4. Only then call `run()` or `Flow.run_async()`.
5. Inspect the returned `RunResult`.

The runnable [review example](../examples/review_flow.py) follows this sequence
using only the core public API. It intentionally includes one failed partition so
that the post-run inspection shows both a failure and a dependency-blocked attempt.

## What to inspect before running

`Flow.plan()` is metadata-only: it validates and returns the declared work without
invoking an asset function. A reviewer should inspect:

- `plan.targets` — the direct targets requested for this run.
- `plan.tasks` — every selected task in deterministic, dependency-first order.
- each `TaskPlan.dependencies` — the direct inputs expected by that task.
- each `TaskPlan.partition_keys` — `None` means one unpartitioned attempt, `()`
  means explicitly selected no work, and a non-empty tuple identifies the selected
  partitions, including falsey keys such as `0` or `""`.
- `plan.config.max_concurrency` and `plan.config.partition_keys` — the execution
  settings that will be used if the caller proceeds.

The example makes its review decision visible as assertions. In an application,
replace those assertions with the reviewer-approved targets, dependencies,
partitions, and configuration; do not treat them as an automatic approval feature.

## Reading the outcome

Start with `result.status`, then inspect every `TaskResult` in `result.tasks`. Task
results stay in plan order, and partition attempts stay in selected partition-key
order. For each attempt, inspect its task and partition identity, terminal status,
duration, output, and—when it failed—`failure.exception_type`, `failure.message`,
and `failure.traceback`.

A `skipped` attempt records why it did not run. A
`dependency_blocked` attempt includes `blocked_by` references; a partitioned task
with an explicitly empty selection is a zero-attempt task with
`no_partition_keys`. A failed partition can therefore coexist with successful
independent partitions, so a task aggregate alone is not enough for partition-level
review.

## Plan, result, logs, and events have different jobs

| Information | When it is useful | What it is for |
| --- | --- | --- |
| `FlowPlan` | Before execution | Reviewing declared targets, dependency structure, partitions, and configuration without invoking assets. |
| `RunResult` | After a normally completed run | Reviewing the structured terminal outcome, timings, in-memory outputs, and failure metadata. |
| Logs | During or after execution | Optional time-ordered progress and diagnostic detail emitted through application-configured logging. |
| `ExecutionEvent` values | During execution | Optional lifecycle observations for an explicitly selected consumer or renderer. They carry event metadata and failure metadata, not a `RunResult`, raw output, or a raw exception object. |

Logs and events do not authorize a run, replace plan review, or replace the final
`RunResult`. An asset failure is represented in a normally completed result; an
external cancellation or a failing event consumer instead propagates an exception
and does not provide a synthetic terminal result.

`RunResult.to_record()` and related `to_record()` methods produce new, JSON-friendly
but intentionally lossy projections. They omit raw outputs, raw exceptions, and raw
partition keys. They do not write a file, create a database, or promise durable run
history. Persistence, schemas, migrations, and record round-tripping are outside
this workflow.

## Review is not a sandbox

Planning and review help a caller understand declared flow structure. They do not
sandbox asset code, prove that it is safe, prevent side effects, validate external
state, or automatically approve execution. `run()` executes ordinary Python, which
may access files, networks, subprocesses, credentials, or external services. The
person responsible for the run must review the asset code and its environment, then
decide whether to execute it—especially for untrusted or AI-generated code.

## Release core-only smoke

To verify the released public workflow from an installed wheel without selecting the
TUI extra, build the wheel and run the core smoke from the repository checkout:

```bash
uv build --wheel --clear
python3 scripts/smoke_wheel_install.py --wheel dist --mode core
```

`--clear` removes stale build artifacts so `dist` contains the one wheel the smoke
will inspect. The helper creates a separate temporary environment outside the source
checkout, installs the built wheel with `pip install --no-deps`, and checks public
import, plan-before-run, and structured result retrieval. It does not import
`kazeflow.tui`. On platforms where the supported Python 3.10--3.13 launcher is
`python` (for example, Windows), use that equivalent interpreter command instead of
`python3`.
