Review after execution

See the outcome, then keep only what you choose.

A completed run explains every task's terminal outcome. Persistence is explicit, local, and intentionally lossy.

Read a result in the terminal

kazeflow run daily.py --yes
kazeflow run daily.py --yes --verbose
kazeflow run daily.py --yes --format json

Text includes the run ID, overall status and duration, then every task in plan order. Failed tasks include portable exception type and message; skipped tasks include a reason. --verbose adds ordered attempt-level status, duration, failure, and blocker detail without raw keys, outputs, exception objects, or tracebacks.

JSON emits exactly one portable RunResult record on standard output. It is the automation boundary; progress and diagnostics remain on standard error.

Inspect the in-memory result in Python

from kazeflow import run

result = run(["publish"])
print(result.run_id, result.status, result.duration)

for task in result.tasks:
    print(task.task.task_name, task.status)
    for attempt in task.attempts:
        print(attempt.status, attempt.output)
        print(attempt.failure, attempt.blocked_by)

The Python result can retain arbitrary output and real partition keys for the current process. result.to_record() creates a new JSON-friendly projection; it does not save anything.

Save a run only when you request it

mkdir -p .kazeflow
kazeflow run daily.py --yes --store .kazeflow/runs.sqlite3

Without --store, execution never creates a database. With it, the CLI creates or initializes the selected SQLite file after a terminal result exists, stores the portable record, then prints the final result. The default history read location is ./.kazeflow/runs.sqlite3, but execution still requires an explicit --store.

Find, inspect, and compare stored runs

# Read the existing default store.
kazeflow runs list
kazeflow runs list --limit 10 --format json
kazeflow runs show RUN_ID
kazeflow runs compare LEFT_RUN_ID RIGHT_RUN_ID

# Read another existing database.
kazeflow runs list --store path/to/runs.sqlite3

Representative text output:

$ kazeflow runs list
Stored runs:
- <run-id> (success; saved_at: <timestamp>; schema: 1)

$ kazeflow runs show <run-id>
Stored run:
- run_id: <run-id>
- status: success
- saved_at: <timestamp>
Portable record:
{ ... }

Run IDs and timestamps vary. Lists are ordered by saved time and run ID. show returns the stored portable envelope. compare preserves left/right argument order and compares run and task aggregates; it does not claim to match individual raw partition keys.

What the SQLite adapter stores

StoredNot stored
Run/task/attempt order and terminal statusesRaw task outputs
UTC timestamps, durations, skip reasons, blockersRaw exception objects
Portable failure type, message, and traceback metadataRaw partition-key values
Whether each attempt is partitionedA reconstructed in-memory RunResult

Falsey partition keys remain distinguishable as “present,” although their original values are not recoverable. Non-serializable outputs, exceptions, and keys therefore do not prevent persistence.

Direct Python storage API

from kazeflow.sqlite_store import SQLiteRunStore

with SQLiteRunStore("runs.sqlite3") as store:
    saved = store.save(result)
    loaded = store.load(result.run_id)
    history = store.list_runs(limit=10)

Constructing a store explicitly creates or initializes schema version 1. Saving a duplicate run ID raises ValueError; loading an unknown ID raises KeyError. Newer, unversioned non-empty, malformed, or incompatible databases are rejected rather than guessed or downgraded. Use one caller-owned store connection per thread; normal SQLite local locking still applies.

Portable by design.

The store is a local adapter, not automatic history, a remote database, a daemon, or a sandbox. Protect the file, choose when to save, and keep the original Python result when raw values matter.

For exit statuses and adapter failure precedence, see the CLI reference. For partition identity boundaries, see Partitions.
