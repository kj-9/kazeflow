## Context

M1--M4 established public, standard-library-only `Flow`, `FlowPlan`, and
`RunResult` APIs, plus an installed-wheel core smoke.  Their roles are present in
individual API documentation, but the recommended human review sequence is not yet
documented as one workflow.  M5 advances the roadmap's reviewability goal without
changing execution behavior or representing arbitrary Python as safe.

## Goals / Non-Goals

**Goals:**

- Document a reproducible public-API sequence: create a `Flow`, obtain and review a
  side-effect-free `FlowPlan`, run only after that review, then inspect `RunResult`.
- Make the sequence useful for code authored by a person or generated by an AI while
  keeping ordinary Python ownership and review responsibility with the caller.
- Explain that `FlowPlan` is pre-execution structure, `RunResult` is terminal
  outcome evidence, and logs are optional chronological detail rather than either
  value's replacement.
- Make the base, installed-wheel public workflow easy to verify with an existing
  release-ready core smoke command.

**Non-Goals:**

- Altering FlowPlan, RunResult, events, assets, scheduling, partitions, failure
  semantics, public exports, package metadata, or optional TUI behavior.
- Introducing AI execution, policy enforcement, sandboxing, security scanning,
  persistence, or any guarantee that reviewed asset code is harmless.
- Requiring Rich, a service, a daemon, or an optional dependency for the core review
  workflow.

## Decisions

### Document review as an explicit caller-controlled phase

The primary example will show `flow.plan(run_config)` before `run(...)`, inspect the
selected targets, dependency-first task order, partition selection, and relevant run
configuration, then inspect terminal result status and attempt outputs/failures.
Planning is the only pre-run structural evidence the library provides; documentation
will say that the caller decides whether to run after review.

Putting these checks into a new approval API was considered, but rejected: it would
change executor semantics and imply enforcement that does not exist.

### Distinguish three information products by timing and purpose

Documentation will describe `FlowPlan` as the immutable pre-execution description,
`RunResult` as the structured terminal summary for the particular run, and logs as
optional time-ordered diagnostic detail.  Logs neither authorize a run nor replace
the result, and a plan cannot predict arbitrary Python effects.

Combining all three into a single “execution report” was rejected because it would
obscure their timing and the existing core contracts.

### Keep the release smoke core-only and public-API based

The release instructions will point to the installed-wheel core smoke already
maintained by M4: first run `uv build --wheel --clear`, then invoke `python3
scripts/smoke_wheel_install.py --wheel dist --mode core`.  Clearing the wheel output
prevents a stale artifact from making the exactly-one-wheel helper ambiguous;
`python3` is the verified system interpreter for this macOS-supported environment.
Windows reviewers can use their equivalent `python` launcher.  The smoke remains
outside the source checkout, installs with `--no-deps`, and demonstrates public
import, side-effect-free planning, execution, and result retrieval.  It does not
validate the optional TUI path.

### Parallel ownership is documentation-first

The README owner exclusively edits `README.md`.  The examples/docs owner exclusively
owns newly introduced review-workflow example or prose files (for example,
`examples/` and `docs/` paths) and must not edit README.  The documentation-test and
smoke owner exclusively owns focused docs/example validation and installed-wheel
smoke command coverage (`tests/` and `scripts/` only).  No M5 owner edits
`flow.py`, `assets.py`, `__init__.py`, `pyproject.toml`, `uv.lock`, or CI workflows.
The root integration owner reviews links and commands serially; OpenSpec sync/archive
remains serial.

## Risks / Trade-offs

- [Readers mistake review for a safety guarantee] → State near each workflow that
  asset code and side effects remain the caller's responsibility; this is not a
  sandbox or security review.
- [Examples drift from public APIs] → Exercise the documented core snippet through a
  focused test or smoke that imports only public symbols.
- [TUI obscures the zero-dependency path] → Keep both workflow examples and the
  release smoke free of `kazeflow.tui` imports.
- [Documentation and example owners edit the same file] → Give README and separate
  examples/docs paths distinct owners; integrate links serially.

## Migration Plan

Existing users keep their current plan/run calls.  Documentation adds the optional
review step and explains the interpretation of the values already returned; no code
migration, rollout, or rollback procedure is required.

## Open Questions

None.  The implementation may keep the review example in README alone if a separate
example file would duplicate it, provided the minimal and review-oriented workflows
remain independently clear and tested.
